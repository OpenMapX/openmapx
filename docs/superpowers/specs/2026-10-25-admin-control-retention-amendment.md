# Renewable control retention amendment

Status: APPROVED for implementation on2026-10-25. Controller self-review and independent review rounds1–4 resolved all material findings: R2 closed clock/quota, R3 closed API delivery/stable-step CAS, R4 closed atomic projection capacity;0 open Critical/Important/Minor. Scope is Task06.1 I5. This is design/buildability approval, not code or runtime acceptance. User explicitly delegated design decisions and waived question/approval gates.

This amendment supersedes only the opaque fresh control-root key/capacity paragraphs in the2026-10-23 control supplement. Original typed effect graph, role-private trust, body/execution fingerprints, immutable deadlines, ownership/settlement and no-replay rules remain. Existing undated records never receive invented origin metadata.

## Intent and decision

An installation must renew terminal evidence storage through ordinary successful use. A permanent1024-operation lifetime quota does not meet remote administration. At least72h terminal evidence and every unresolved/unknown family remain protected. Reclaimed old authority must never become a fresh effect.

Three approaches were evaluated:

1. Delete old opaque identities behind a time watermark: rejected. The real sequential probe in task-06.1-report.md demonstrates same-key/body admission receiving a fresh deadline after deletion.
2. Certified issuer sequences and retirement floors: feasible in principle, but require new issuance, cutover and cross-role sequence machinery. A counter assigned only at admission does not identify replayed old opaque keys.
3. Self-describing immutable root expiry, bound by existing authenticated/signed identity: selected. The key itself retains its last admissible time, independent of stored historical membership. Changing that time changes the key. A caller-chosen expiry is only a restrictive validity input, never role/target/privilege authority; server policy and existing signatures/bearers still enforce access and actual execution budget. This adds no key-minting network service.

## Root key contract and admission

`createControlRootOperationKey({notAfter:number,nonce:Uint8Array}):string` and `parseControlRootOperationKey(key:string):{notAfter:number,nonce:string}` live in core ops/control-root-key.ts (browser-safe pure format/hash helpers; no private trust export). Format is `opk1_t1_<14 lowercase hex expiry digits>_<22 canonical base64url nonce characters>`. Nonce is exactly16bytes, encoded without padding. Expiry is a positive safe epoch-ms integer, canonically zero-padded to14hex digits. Root suffix length40 fits the existing opk1 validator; the exact32-character phase-key hash format remains distinct and unchanged. No expiry is derived from HTTP issuedAt/expiresAt.

A fixed producer chooses the root absolute requested deadline and key BEFORE its first mutation submission and persists both before dispatch. API uses a deterministic16byte nonce from domain-separated SHA256(namespace,durableAPIjob/step identity); host CLI/cron uses cryptographic16byte randomness persisted with its local attempt. Observers reuse the exact checkpoint. No renewal, same-key fresh deadline, or prepare-after-lost-mutation fallback exists.

For a previously unseen authority-bearing root, require a timed root key, explicit `requestedDeadlineAt === key.notAfter`, and `0 < notAfter-now <= 7days`. Normalized runtime deadline remains the minimum of requested, deployment/kind and verified API-parent bounds; the key cannot enlarge it. An elapsed key is expired/unknown before any admission reservation/effect, even if its historical details are gone. Duplicate retained reads/cancel/settlement remain possible after expiry; they never authorize new forward work. Existing exact retained normalization/conflict rules remain.

A derived fixed child keeps the existing phase-key formula and must carry verified inherited origin through its role-signed parent/lease/fixedCLI chain. An undated hash is not admitted as a new standalone root. A deadline-only child acquiring its independent target lease inherits the same origin, even though its executor differs. Its local durable execution and key are still its original distinct identity.

`ControlExecutionOrigin = {version:1,rootKey:string,issuer:ControlIssuer,notAfter:number}` is internal non-secret metadata, signed within existing execution admissions/witnesses, lease certificates and child grants. Root construction derives it from the authenticated fixed executor and parsed key; child construction derives it solely from the verified parent's retained signed origin. No request boolean, JSON origin object, unsigned env field or cast creates nominal origin authority. Every child/retained duplicate checks exact origin continuity and deadline<=origin.notAfter. Public ExecutionRef shape need not change; origin is separate signed immutable authority evidence and a bounded private retention index key.

## Renewable bounded retirement

Keep bounded active and retained capacities, with before-effect refusal if capacity genuinely cannot be reclaimed yet. Capacity is retained-window/unresolved pressure, never a lifetime operation counter. Roots still valid, families terminal for less than72h, and any unresolved/attempted/unknown effect or descendant cannot be reclaimed. An unadmitted issued root is not a mutation attempt, but its partial private admission must be conservatively contained before retirement.

Use existing per-role private roots, shared signed ledgers and writer guards; no generic service. A bounded per-origin family index records the exact fixed namespaces/basenames/keys/slot identities owned by that family (no arbitrary paths), plus durable GC phase/cursors. New writes reserve index/counter capacity before publication. Size/count limits and maximum fixed descendants remain enforced. Admission looks only at bounded active slots/index pages; retirement is incremental and must not turn its5s admission budget into historical synchronous scans.

An origin family is eligible only after: (a) `now >= origin.notAfter`; (b) at least72h since its last authoritative terminal transition; (c) every local effect, lease and attempted descendant has authenticated terminal/contained evidence; (d) root and all shared target nodes are authoritatively settled with exact physical ownership, and no helper/stream/worker handle can still perform effects; and (e) cross-role evidence/settlement needed by any still-unresolved parent has been retained or acknowledged. Age/deadline/PID alone never supplies c–e.

Retirement uses a bounded, signed journal and exact ownership/CAS. First persist the irrevocable expired/no-forward decision and complete evidence manifest; then reclaim only listed settled private/shared records and keys, with role-local ownership; finally return index/namespace/history slots. Crashes leave resumable exact progress or safe refusal, never a free slot without durable no-replay/containment evidence. Other roles acknowledge their own private cleanup; no role writes or reads sibling-private material. Before removing the final shared evidence, each participating role must either hold the exact signed terminal/retirement proof it needs or acknowledge that it no longer needs it. A missing/corrupt participant remains fenced; it is not treated as cleaned. A bounded pending-retirement family may consume capacity until the role returns and reconciles, without requiring ordinary successful families to stop the host.

A retired timed root can be recognized as expired directly from its unchanged key. Retired undated child hashes cannot become roots and cannot be newly adopted without the original valid signed chain; expired/missing chain produces unknown/expired. Reclamation does not require one permanent tombstone per old key, issuer sequencing, a lossy membership filter or reset of installation trust. Preserve at least72h exact lookup; afterward return expired/unknown without manufacturing not-started/canceled success.

## Producer and compatibility cutover

Task06.1 owns pure key/origin/retirement foundation, current host/fixedCLI constructors, actual agent receiving adapters, and current API root operation-key producer where necessary for coherent use. Task02.3/02.4 and01.2 consume the same helpers in their new durable data/config workflows; do not invent competing keys or origin stores. API CAS checkpoints both deadline and final timed key before signing or submitting. No root issuance HTTP endpoint is added.

Existing v1/v2 status, lookup, cancel, result/failure wire shapes stay readable. Already-retained undated operations remain observation/settlement-only and are never replayed or stamped with a guessed origin. Missing old undated roots cannot enter the new authority path: reject before mutation with a fixed actionable client-upgrade prerequisite. Ordinary non-authority read operations remain compatible. This explicitly narrows the earlier old-client/new-agent promise for fresh authority-bearing mutations; the upgrade must install agent verification first, then current API/CLI producers, before those actions are offered. Preserve legacy wire parsing rather than silently normalizing old keys as fresh authority. An unsupported root-key scheme is a prerequisite rejection, not backend success or an unknown attempted effect.

Existing pre-index/private protocol records are experimental/unreleased on this branch. Retain them fail-closed for exact lookup/settlement and supervised reconciliation; never silently migrate them into forward authority. New retention cannot delete them merely because they lack origin. Test fixtures for new authority use timed keys or verified inherited origin. Production checks must explicitly distinguish legacy reading from current managed admission; no claim of transparent old undated mutation support.

## Self-review and review focus

This removes the exact-membership contradiction by changing the fresh root identity acceptance rule, rather than pretending a timestamp authenticates a role. Exact old key expiry is immutable in the request key and rejected against the durable retirement floor below; changing it is a different authenticated operation. New kind/deployment clamps remain independent. Derived descendants cannot escape through an undated root fallback. Family GC must not remove another unresolved role's only evidence. No remaining audit scope is deferred.

Review/test counterexamples: delete expired terminal details then re-normalize exact root key; change a requested deadline while retaining key; take an old phase hash as a fresh root; recreate a child through a deadline-only parent after root retirement; keep one unresolved early family while many later families expire; kill each role between signed retirement and private deletion/slot reuse; offline participant returns; duplicate observation during retirement; stale index/high-water/slot inode; missing private evidence; prepared helper still active. All must reject or retain the original fenced state without duplicate effects or unbounded history growth.

## Revision2 binding decisions — amendment review I1–I4

The following concrete contracts resolve the review; they supersede any less specific language above. This is still a reviewed-before-code amendment, not approval of an implementer's future collector.

### Durable expiry barrier (I1)

Each role has one installation-bound signed private `retention-clock.json`, preallocated during verified empty-store bootstrap: `{version:1,installationId,role,sequence,lastRetirementWallTime,rejectNotAfterThrough}`. Sequence is a safe nonnegative monotonic integer; the time fields are safe epoch-ms integers. The private writer/physical identity and private high-water/CAS discipline are the same as existing execution state, including bounded read, no-follow, single link and fsync. Missing/corrupt/rolled-back clock state in a nonempty store disables fresh control authority and retirement; it never silently bootstraps a zero floor. A simultaneous rollback of the trusted host's entire private installation/key backup is outside online recovery and requires the existing supervised restore boundary.

Before a role deletes any replay evidence for an origin, it durably advances `rejectNotAfterThrough` to at least that origin.notAfter and `lastRetirementWallTime` to at least the current retirement wall time, under the same journal transaction; other participant roles do so before their private deletion too. Every fresh root admission/retained descendant forward authorization rejects origin.notAfter<=the relevant durable floor. While wallNow<lastRetirementWallTime, new forward authority and new retirements fail with an actionable clock-recovery prerequisite; existing observation, cancel and contained settlement remain usable. There is no backward floor correction or automatic key rotation. Read-only lookup may return retained terminal evidence below the floor and never creates authority.

A role can preserve unresolved older origins below an advanced global floor: the floor denies new forward work only, not their exact lookup/cancel/settlement. Ordinary unrelated origins with notAfter above the floor can continue once clock checks pass. A backward wall clock after full GC/restart cannot resurrect the old exact key even with a newly normalized deadline. The retention-age guarantee uses the host's wall-time service, as existing deadline/authentication policy does; the durable barrier specifically prevents post-retirement replay after clock correction. Unexpected forward jumps may conservatively cause a clock prerequisite after correction, never a replay allowance.

### Origin and external parent boundary (I2)

An API HMAC parent remains a deadline/attempt bound, not a role origin. An API-parented fresh timed operation on the agent creates a new ops-agent origin; its exact API parent/attempt is an external receipt dependency. Host CLI/cron roots create their own role origin. Derived role children inherit the signed origin; independent child target leases do too. No API role key or generic signing service is added. Existing version1 signed records remain legacy observation-only. New origin-bearing signed records are version2 and use version2 domain strings, including the version in signatures; verifiers never parse an old record as a new origin-bearing shape.

The coordinator is origin.issuer (the role owning the original timed root), with one bounded family slot/generation UUID. Same-role fixed CLI descendants are part of that role's participant. The participant set contains only actually enlisted roles and at most one external API parent; it is not all configured roles. A role is enlisted durably before exposing a grant/attempt that may reach it. Attempted/unaccepted/lost-response children enlist the recipient; only a signed exact never-exposed/no-effect proof can eliminate an unused prepared intent. Independent child leases enlist under the same origin. Once all nodes are terminal/contained, membership closes under the root journal CAS; no later grant/effect/participant can be added. A late conflicting intent makes preparation fail closed.

The frozen `RetirementManifest` is signed by origin.issuer, at most128KiB: `{version:1,installationId,origin,familyId,generation,sequence,terminalAt,terminalSequenceDigest,participants,executionReceiptDigests,sharedRecordSetDigest,localRecordSetDigests}`. Digests are64 lowercase hex; IDs UUID; participant IDs are finite role names or `api:<apiJobId>:<attemptId>`. Maximum128 executions and256 total retained child intents per origin (existing tighter per-node64/depth2 limits still apply). Max3 role participants plus1 API parent. A larger prospective family is refused before its extra effect/admission. TerminalAt is the latest authoritative terminal transition, not first completion or observer close.

The API dependency is satisfied only after the API durably CAS-copies this operation's exact terminal identity, normalized deadline, safe result/failure/publication evidence and digest into its private job checkpoint. An unresolved API parent retains that copy; terminal parent cleanup preserves it at least72h afterward. Missing/uncertain DB write sends no acknowledgement. Add fixed API-only sync15s typed operation `controlRetention.acknowledge` with `{originRootKey,operationKey,fingerprint,terminalDigest,proof}`; request<=16KiB, result `{acknowledged:true}`. `proof` is the existing API ops-token HMAC with domain `openmapx-api-retention-ack-v1\0`, over strict canonical fields `{version:1,apiJobId,originalApiOwnerVersion,attemptId,checkpointOwnerVersion,terminalCopyId,operationKey,fingerprint,terminalDigest}`. TerminalCopyId UUID and owner version are persisted in the same successful checkpoint CAS before minting. Agent validates API role, HMAC, exact original parent/attempt/operation and its current terminal digest, and persists the ack in the preallocated family cell. Different identity/digest conflicts. Response loss is safe to observe/repeat this exact proof; it cannot dispatch a host effect. No browser route accepts it.

Core server-capable ops exports `controlTerminalReceiptDigest(status:OpsJobStatus):string`. It validates version2 terminal `succeeded|failed|timed_out` with the existing strict per-kind result/failure parser, then domain-separated SHA256 of canonical `{version:2,operationId,operationKey,kind,admittedAt,deadlineAt,fingerprint,state,terminationRequestedAt:null|string,errorClass:null|string,result:null|typedResult,failureResult:null|OpsFailureResult}`. Missing optional fields use null; progress/diagnostics/update time are excluded. API and agent use this identical helper. The private copied terminal receipt is bounded128KiB, retains safe publication evidence inside the existing result/failure contract, and is not sent in the acknowledgement.

The API ack may arrive before the GC manifest exists: it binds exact operation+terminal digest and original attempt, and the later manifest includes that same executionReceiptDigest. It does not claim knowledge of an unfrozen manifest. An API parent still unknown with no durable receipt copy prevents retirement of that family, even if all three role workers are locally terminal. This is independent of unrelated eligible families. API observer recovery retries acknowledgement from the retained checkpoint; it never reissues the original mutation to obtain it.

### Retirement state machine and acknowledgement authority (I2/I3)

Every participating role writes only its own role-private progress and its separately signed shared acknowledgement cell. Coordinator writes the shared decision cell. Paths derive solely from validated origin/family/role IDs under fixed roots; sibling-private access remains forbidden. Shared participant ack payloads are `{version:1,installationId,familyId,generation,originDigest,manifestDigest,role,phase,terminalSequenceDigest,recordSetDigest,proofCopyDigest,sequence}`, signed by that role's fixed key. Phase is `ready|clean|released`; sequence is monotonic. Exact manifest/generation/digests must match; an ack for another family, state or prior slot occupant is invalid.

The API ack is evidence-copy-before-ack, not a permission to erase an unresolved API parent's DB copy. Its digest participates in prepared/commit proof; a fourth role-private mount is unnecessary. After all released a role's GC proof has no remaining dependent parent: API holds its own copy, role children/root are terminal and retired, and the expired self-describing key plus durable floor prevents fresh replay. Therefore retirement cells and keys can be reclaimed without a permanent tombstone. A role that crashes after released but before local workspace removal uses its already-private final copy and slot generation; it needs no deleted shared evidence.

Observers participating before membership closes retain exact proof via existing admission/attempt identity; ordinary human read requests hold a transient descriptor guard, not a permanent new participant. Deletion waits for those descriptor callbacks to settle. Late reads after the72h/expiry retirement boundary return expired/unknown, never a fabricated terminal result. Missing enlisted roles/acknowledgements, attempted unaccepted children and corrupt records remain pending; PID age is not cleanup authority.

### Reserved collector workspace and exact accounting (I3)

Ordinary capacity remains1024 retained families per role and256 active leases, with256 retained child intents/128 executions per family as above. Before exposing its first family assertion/admission, each role reserves a family slot and preallocates its GC progress/proof cell outside ordinary namespace counts. Shared coordinator and max3 participant ack cells are preallocated at root admission/enlistment. Reserving the last ordinary record cannot consume these cells. Slot inode+generation UUID is retained and checked on every reuse.

Per-role/per-family index records at most4096 owned records/keys in64 pages of64 entries, each page<=16KiB; each entry is a fixed namespace+validated basename+record digest/inode+ordinal. Total reserved GC/index metadata is capped2MiB per role/family, including one<=128KiB progress/proof cell and prebudgeted ack/decision records. These bounds are separate from ordinary128KiB receipt limits. Index page capacity is reserved at family admission; publishing a new ordinary record requires its ownership entry/creation reservation first. Only the enumerated fixed namespaces are allowed. GC reads a page at a time and maxFamilies defaults16/range1–64. A durable round-robin slot cursor advances past pending families so an early unresolved family cannot starve later eligible families. No admission lists/parses lifetime history.

Retirement creation/updates use preallocated cells, even at full ordinary quota. Physical IO failure/ENOSPC still causes safe pending/refusal, not a false freed slot; deployment disk-resource qualification remains required. No new retirement record per completed operation survives final workspace release.

Namespace quota changes use one fixed preallocated transaction cell under that namespace's existing owned writer guard. Payload identifies family slot/generation, manifest digest, record ordinal/inode, before/after count and phase `planned|unlinked|counted|item_done`. Persist planned before unlink. Unlink only exact inode/owner and fsync directory. Persist unlinked, then counted with the exact decremented count; keep that same transaction identity until the family progress cell durably records item_done. Clear it only afterward, before another adjustment. A crash after unlink is accepted as this authorized deletion only with the matching planned transaction, not generic ENOENT. A crash after decrement cannot decrement twice because counted transaction is retained until item_done. Replaced inode/digest or mismatched counter/version fences recovery. Counter decrease never precedes physical deletion.

History/namespace/family slot release similarly journals the exact slot inode/generation and returned-capacity phase before reuse; a new occupant has a different generation and cannot be deleted or decremented by an old continuation. Uncertain writer containment cannot steal its guard; existing verified recovery authority must prove the exact writer contained before finishing its retained transaction. This may require the documented offline failure-recovery boundary after a real uncontained control-plane failure; ordinary success/full quota does not. Tests distinguish contained crash resumption from unknown ownership. A restart uses only this exact journal, never recomputed current counts or unconditional counter reset.

### Stable API step address and checkpoint version3 (I4)

Keep `createDurableOpsKey(namespace,durableIdentity)` as a stable logical step address. `ExecuteAdminJobOperationOptions.operationKey`, when supplied by existing API callers, is that address as well; it is not directly translated at the transport after lookup. Add private `OpsProjection` version3 with `steps:Record<stepAddress,{operationKey,requestedDeadlineAt}>` and `operations:Record<finalOperationKey,ProjectedOperation>`, at most64 entries in each. Existing operation/result/event bounds remain. Mapping and complete typed operation/attempt/parent checkpoint are committed in ONE existing owner-fenced CAS before signing/POST.

`executeAdminJobOperation` first computes the timeless stepAddress and reads/resolves the mapping before reading time or creating input. A retained mapping wins: reuse exact final key/deadline/body/attempt and observe only. `retainedAdminJobOperation`, `hasRetainedAdminJobOperation`, `observeRetainedAdminJobOperation`, resume and cancellation helpers all resolve stable address first; old literal final-key lookups remain usable internally. Trusted configuration's pre-preparation gate at trusted-config-operations.ts uses this resolver before rebuilding desired config or taking a fresh snapshot. Its `_configurationOutcomes` can remain keyed by the stable address.

For an absent address only: choose/persist the parent budget and requested absolute child deadline, derive the timed key using that deadline plus deterministic16byte nonce from jobID+stable address, prepare its exact API attempt, then CAS-save mapping+operation+attempt+parent together. A failed/unknown checkpoint never signs or POSTs; DB reconciliation must resolve the original row before another owner treats the address as absent. After any attempted POST, recovery never creates a replacement mapping or re-prepares desired input. A caller's changed supplied address is a different explicit logical step; the same address cannot renew a deadline.

Legacy projections versions1/2 resolve their existing `operations[address]` directly; never invent a mapping/deadline/origin for them. Already-attempted old entries are lookup-only. A retained pre-admission legacy entry without conclusive not-submitted proof remains unknown/prerequisite; it is not normalized as a new timed root. Fresh v3 entries need a real durable JobContext owner; mocks must supply that context rather than bypassing it. Signed fixed control children outside this API-root broker retain their exact phase key; this address mapping does not re-key delegated children.

## Revision3 binding decisions — remaining amendment I2/I4

### Recoverable API receipt delivery obligation (I2)

Choose completion gating in the existing durable API job, not a new outbox table/service. Each fresh v3 projected operation stores `receiptDelivery: {state:"pending"|"confirmed", terminalCopyId:UUID, checkpointOwnerVersion:number, terminalDigest:string, terminalReceipt:OpsJobStatus}`. The original attempt/API parent plus the exact checkpoint owner version/copy ID are retained for deterministic re-signing. A terminal receipt and pending delivery obligation are CAS-written together before sending any acknowledgement. The terminal status is validated and bounded128KiB as above. Public projection strips this private metadata; existing safe operation failure/result remains truthful.

EVERY terminal consumption path calls `ensureAdminJobReceiptDelivery` before returning/rethrowing a cached result/failure: newly observed terminal, cached terminal on restart, terminal-before-cancel, and failure/cancellation reconciliation. Exact pending proof may be resent; the original mutating operation may not. Ordinary observer/worker abort does not abort the durable delivery obligation; its network attempt uses a separate bounded15s observation signal, and failure schedules the existing bounded job reconciliation/backoff. Parent stays `running` or `cancel_pending` with `JobObservationPending("receipt_delivery")` while delivery or its confirmation checkpoint is uncertain. Do not misclassify receipt delivery as unknown backend effects: the authenticated terminal operation result is already in the checkpoint. Its final outcome is preserved and returned/rethrown only after delivery is durably confirmed. Success that preceded cancellation remains success; a known failure remains failure.

`job-runner.ts` enforces this completion gate on every success/failure/canceled finalization in BOTH code and its owner-fenced SQL predicate: no terminal write while any v3 projected receiptDelivery.state is pending. The check uses current DB JSON, not only the handler's stale result. Existing reconcile selects this nonterminal job and resolves only retained operations/receipt obligations; it never repeats a handler mutation. `ensureAdminJobReceiptDelivery` executes on cached terminal entries before their current early-return branch. On confirmed agent response, CAS-mark confirmed; a lost confirmation write leaves pending for exact retry. All admin-job cleanup/expiry/delete predicates prohibit deleting the last terminal copy while pending, regardless of parent status. Correct new code cannot create a terminal parent with pending delivery; existing terminal v1/v2 jobs do not acquire an invented acknowledgement obligation. A missing/invalid pending copy is a recovery-required job, not a fresh action.

Lost response after agent persistence must not strand an API job after GC. `controlRetention.acknowledge` reaccepts the exact valid HMAC proof in these finite cases: (1) retained family/operation exists: exact API parent/attempt/terminal digest match, persist or observe identical ack; (2) no retained family or partial-index/GC entry exists, root key is syntactically timed and originRootKey==operationKey, and its expiry is at/below the durable role rejection floor: return `{acknowledged:true}` as DISCHARGE OF A RECEIPT DEPENDENCY ONLY, creating no retained record or authority. The proof must still validate against the fixed API token and its exact canonical fields. The API already owns the authenticated terminal copy. This response asserts neither operation success nor that an unknown job ran; it only states the agent has no retained dependency to await. If any index/GC/semantic record suggests missing/corrupt/partial retained state, return pending/recovery-required instead. No absence-only discharge for an unexpired key or unsupported legacy key. Never reconstruct terminal effects from404/410.

Thus an ack persisted but response lost can finish after full GC without one ack tombstone per historical key. If the request never persisted, the retained family cannot have retired because its API dependency is still pending; the resend compares and writes that exact acknowledgement. The API clears its delivery obligation only on the authenticated success response followed by confirmed checkpoint CAS. After confirmed delivery, unresolved API parents still retain their copied terminal evidence; terminal parents retain it at least72h. Cleanup cannot race a pending obligation. This is routine retry of a no-host-effect acknowledgement, never replay of the original command.

### Atomic stable-address reservation and same-owner races (I4)

Extend `JobContext.checkpoint(result,progress?,admissionKey?,stepAddress?)` with the fourth optional stable step address; existing legacy three-argument behavior remains for v1/v2 records. For fresh v3 allocation, admissionKey is the candidate final timed key and stepAddress is the timeless logical address. `job-runner.ts` performs ONE owner/version/active-status fenced DB update with all predicates: (a) `opsProjection.steps[stepAddress] IS NULL`; (b) `opsProjection.operations[stepAddress] IS NULL` (legacy address protection); (c) `opsProjection.operations[admissionKey] IS NULL`; (d) retained parent is absent or exactly the candidate parent; (e) fresh-admission cancellation guard still permits new work. Validate the complete v3 mapping/body/attempt/deadline before this update. It is not the old final-key-only null test.

The DB update merges only this reserved step/mapping and its operation into the CURRENT DB JSON; it does not replace a caller's whole stale opsProjection. Preserve other addresses, operations, event counters, observer lease/owner state and unrelated checkpoint members. Return the full updated checkpoint from DB and assign ctx.checkpointResult only after confirmed success. Parent-attempt preparation is pure until this CAS: `prepareApiJobChildAttempt` must not mutate ctx.checkpointResult or publish a parent before the allocation wins. Candidate parent fields are included in the same atomic update.

If no row updates: distinguish actual owner loss from stable-step/parent conflict by a fenced read of the owned row. Owner loss retains existing JobOwnershipLost behavior. Same-owner losing allocation refreshes ctx.checkpointResult from the winning DB mapping and raises distinct `JobStepAllocationConflict`, which the broker resolves by observing the winning original key/deadline/body with fresh=false (or JobObservationPending if the winner is not yet observable). The loser neither signs nor POSTs and never chooses another deadline. A failed/ambiguous DB write is persistence uncertainty, not a winner or permission for another allocation; reconcile that same address from DB. An overwritten winner is impossible because the stable-address null predicate is atomic. If the first commit is ambiguous, zero submissions is allowed; later lookup remains unknown rather than resubmitting.

Non-admission v3 projection writes also preserve mappings and unrelated entries using identity-conditioned per-entry updates; a stale whole snapshot cannot erase another address, reverse confirmed delivery to pending, replace immutable input/attempt/deadline or turn terminal back into observing. New entries/mappings are permitted only by the reservation path. Existing serialized checkpointTail is useful local sequencing but is not the database uniqueness proof. Legacy entries are still resolved by literal address before allocation, and final-key internal lookups are read-only aliases. Include concurrent distinct-address preservation as a covering test alongside same-address one-winner tests.

## Revision4 binding decision — atomic projection capacity (R3-N1)

The SAME current-DB reservation transaction/update that enforces stable-address uniqueness must validate the POST-MERGE cardinality of BOTH maps: steps<=64 and operations<=64, including every retained legacy operation. It must use current row state under its write/row lock, not the caller's earlier snapshot; candidate validation or post-write parsing alone is insufficient. An equivalent row-locked transaction must check these limits before committing the mapping. No invalid65-entry row may ever be persisted.
