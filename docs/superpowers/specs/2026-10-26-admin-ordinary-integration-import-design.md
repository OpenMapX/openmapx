# Task01.2 current ordinary integration-config import ruling

Status: APPROVED allocation ruling after independent R1 READY (0 Critical / 0 Important). This is an allocation correction inside the existing 50 tasks, not a new task or a generic authorization mechanism. ## Problem, decision and alternatives

The current `importAdminIntegrationConfigs` route accepts a batch of installed integration configuration entries. `prepareIntegrationImport` validates known nonsecret fields and the existing boolean `enabled` field; the old `persistIntegrationImport` replaces target config rows before a full trusted snapshot is sealed. Protocol5.1 requires multi-target imports to use purpose `migration` and its nominal `configuration-migration` participant, while allocating that constructor to future04.5. Task01.2 simultaneously requires all current configuration producers to use preflighted retained candidates. These statements cannot all hold without an explicit subcase allocation.

Ruling: move ONLY the adapter for this existing ordinary integration-config import forward from04.5 into01.2. Put it in the owning built-in module `apps/api/src/services/configuration-migration/legacy-integration-import.ts`. It constructs the existing `configuration-migration` participant for its closed **legacy-integration-config** intent. Use existing purpose `migration` and operation `stack.render`; do not add a participant kind, purpose, generic registry or ordinary multi-target bypass. The staged migration/auth/binding adapter remains04.5 and uninstalled; credential-import, transit-credentials and integration-binding adapters remain their assigned later tasks.

Alternative defer the existing import until04.5 contradicts01.2's current-producer cutover. Alternative treat arbitrary multi-target changes as ordinary configuration would bypass the finite participant contract. Installing all04.5 now would prematurely pull in auth drafts, bindings, UI and migration receipts. The selected narrow adapter preserves current functionality with no additional privilege.

## Closed intent and authority

The module exports a fixed constructor/preparer for the existing route's body plus the live `AdministrativeConfigurationWriter`. It obtains integration schemas/registry and prior state through that writer's strict captured read context. It calls the actual existing `prepareIntegrationImport` validation; it does not accept caller-provided schemas, authorization callbacks, participant objects, purpose strings, proof handles or an asserted validated flag. The resulting intent is nominal, frozen and bound to this writer instance, actor, operation, exact normalized entries, lock-set, observed row identities/versions, registry/schema observation and exact overlay. Reusing it under another writer or operation, changing its batch, or forging a structural object rejects. Internal brand issuance must be fixed to this actual built-in producer; no exported arbitrary callback/registration surface. A private optional subcase discriminator is not wire authority.

Only installed, declared integration IDs and `integration-config` overlay changes are permitted. Entries contain schema-writable NONSECRET ordinary keys and the current special boolean `enabled`; this is the existing integration enable flag, not a capability binding or selected-service change. Retain existing `prepareIntegrationImport` behavior for supplied schema-secret fields: omit them without returning their values. They never enter the candidate intent, typed envelope, audit or job metadata. No integration/service vault mutation, managed feed map, service configuration, selection, platform value, auth setting, binding or arbitrary SQL mutation is admitted through this subcase. No new reauthentication policy is invented for this existing admin-only nonsecret operation.

Keep the route's nonempty/unique-ID/schema bounds and the whole prospective overlay limits, using the smaller effective bound. Batch import REPLACES each target's declared ordinary DB fields: set supplied ordinary values, unset omitted existing declared ordinary keys, preserve the previous boolean enabled when omitted (apply explicit true/false), and preserve vault entries and any schema-secret legacy DB values. No secret is converted into an ordinary unset. Unknown/undeclared legacy rows or incompatible fields receive the existing strict sanitized correction diagnostic; do not silently discard them to make the candidate fit. The legacy secret-preservation rule deliberately prevents a nonsecret import from deleting credentials. Unrelated integrations and all unchanged state remain included and unchanged. An empty effective patch is a no-op with truthful metadata, not a fabricated application.

All proposed effective set/delete changes obey default < database < vault < config.json < env and01.2's host-source witness rules. Validate host/file ownership before persistence; compare any source observations again before commit. A pure unchanged entry does not constitute adoption or authorize overwriting a host source.

## Participant and atomic cutover

The fixed participant is mode apply, kind configuration-migration, managedServiceSecretKeys empty. `authorize` validates its live writer/actor/job/lock set and closed intent before candidate preparation. `verify` binds the exact retained candidate/overlay and original row/schema/source observations before persistence and again inside the candidate transaction. `commit` validates that same immutable import identity on the supplied writer transaction; it performs NO auth/binding/proof/vault/managed-feed writes. Generic overlay persistence is the SOLE writer of the ordinary config rows. A fixed read-only verification/no-additional-writes commit is legitimate here; it is not a fake reauthentication or proof consumer. Unsupported future migration intents still reject at construction, not via caller-selected empty proof requirements.

Flow: current authenticated route -> retained stable API job -> global writer -> sorted complete batch integration locks -> fixed built-in import intent/participant -> prepare full candidate -> exact seal/size/source/private queue preflight -> one candidate DB transaction containing ordinary overlays + job checkpoint -> original retained typed apply -> awaited integration reload/evidence. No `persistIntegrationImport` before candidate preflight, no second global-pool transaction, no per-entry applies, no reconstruction/reseal from later rows. Generic participant `verify` and transaction behavior remain protocol5.1. Ordinary import alone does not claim a managed-map maintenance exception; if the frozen follow-up genuinely recreates DM, existing5.4 preparation/decision/settlement is mandatory.

Retain original candidate/revision, stable operation key and unknown/apply evidence under the current job protocol. HTTP/browser callers must consume that retained job/result through the standard coherent contract cutover, not receive a permanent upgrade-client or unavailable-participant response. Count imported entries only after desired commit; application/reload failed or unknown must not report complete success. Keep audit event integration.config.import with nonsecret IDs/count/outcomes. Do not reuse legacy in-memory `saved.owns/restore` closures after restart. Desired committed rows remain visible with failed/unknown application until explicit authorized reconciliation; any existing conditional compensation may remain only if it proves exact ownership and is expressible within the original frozen candidate/effect authority. No blind rollback, fresh root or automatic mutation retry is introduced.

04.5 extends the owning migration module with a SEPARATE fixed constructor for validated pending-auth drafts and selected-binding CAS. It must reuse the shared candidate/participant/writer path and this ordinary-import adapter where applicable; it may not reinterpret a legacy intent as proof of auth/binding authorization. Existing03 proof and05 managed-feed contracts remain unchanged.
