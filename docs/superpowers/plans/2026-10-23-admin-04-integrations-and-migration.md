# Integration Ownership and Migration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Activate binding/configuration changes honestly, manage standalone declarative installations, and provide bounded configuration/credential migration, covering I01–I06.

**Architecture:** Extend the existing configuration ownership, revision-CAS, extension journal and staged integration reload paths. Separate desired database state, effective runtime state and installation provenance; migration inventories are safe projections, while vault values travel only in an explicitly reauthenticated encrypted envelope.

**Tech Stack:** TypeScript, Fastify, Zod, Drizzle/PostgreSQL, typed ops-agent, integration-framework installer, Node crypto/Web Crypto, React/MUI, Vitest.

**Spec:** `docs/superpowers/specs/2026-10-23-admin-instance-management-design.md` and binding `docs/superpowers/specs/2026-10-23-admin-control-protocols.md` §5; controller: `docs/superpowers/plans/2026-10-23-admin-instance-management.md`.

## Global Constraints

- All product work stays in this worktree; preserve unrelated work and existing
  public-provider behavior. One branch/PR; no merge or production deployment.
- Use Codex provider instances only for delegated work.
- Retain `IntegrationContext`, HTTP/upstream acquisition, attribution and source
  policy boundaries. Community integrations remain declarative; no uploaded code
  execution and no browser developer toolchain.
- Docker, registry credentials, privileged host files and host data writes remain
  behind typed ops-agent operations. No generic command, arbitrary path or raw
  environment-file editor is introduced.
- Core API routes use `registerCoreRoutes`, runtime admin guards beside auth
  declarations, strict schemas, audit events, explicit mutation identities and
  appropriate rate limits. Privacy roles retain their narrower authority.
- Contracts precede generated outputs. Serialize OpenAPI/SDK generation; never
  hand-edit generated files. Check actual response serialization.
- Preserve configuration writer ownership, revision CAS, admission fingerprints,
  durable operation identities, retained results, unknown outcomes and cancellation
  fences. No automatic mutation retries or unproven rollback/compensation.
- Use synthetic/public data in tests and UI verification. Never print secrets,
  place secrets in argv or logs, or copy private operator data into artifacts.
- Stream large transfers with bounded memory, disk budgets, timeouts, cancellation
  and cleanup. Opaque IDs cross trust boundaries; host paths do not.
- UI controls expose availability and reasons before submission. A successful
  admission means queued, not applied. Failed/partial/unknown work stays visible.
- Inspect the actual rendered desktop/mobile UI locally. Do not upload screenshots
  to the PR, as explicitly requested.
- Complete focused checks, full local verification, relevant disposable database
  and runtime checks, independent review, production builds and PR CI. Report any
  unavailable environment gate distinctly; do not replace runtime evidence with
  mocked assertions.

Planning boundary: no product edits, dependency installation, generators, builds, tests, or commits while authoring. Read root/web `AGENTS.md`, API surface, integration system, built-in/external integration guides, service-manifest ownership contract, and Contributing quality bar. Baseline: `ef896ceae876959180116cf61ffcf643b88ebffe`.

## Review Focus

1. A binding reload reads stale/unavailable authority or overlaps another edit: never report the saved binding as active without matching runtime evidence (Task 1).
2. A file/environment value shadows a database save or vault rotation: reject the ineffective write before persistence, disclose ownership, and never reveal the secret (Task 2).
3. A legacy directory is replaced or claimed between preview and adoption/removal: fingerprint/ownership conflict prevents deleting another install (Tasks 3, 4).
4. Migration targets differ in manifests, selected services, or host overrides: preview names omissions/prerequisites and stale preview cannot apply (Task 5).
5. A hostile envelope requests huge KDF work or has altered metadata/ciphertext: reject before expensive work or any database/host mutation (Task 6).
