# Account Policy and Provisioning Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make account policy effective and provide safe, auditable account provisioning and recovery, covering A01–A10.

**Architecture:** Resolve one immutable policy per auth operation and build Better Auth instances from that policy. A transaction-bound auth adapter and database invariant protect every remote account mutation; focused account services provide reauthentication and provisioning without enlarging the general admin route.

**Tech Stack:** TypeScript, Better Auth 1.7.7, Fastify, Drizzle/PostgreSQL, Zod, React/MUI, Vitest.

**Spec:** `docs/superpowers/specs/2026-10-23-admin-instance-management-design.md`; execution/controller gates: `docs/superpowers/plans/2026-10-23-admin-instance-management.md`.

## Review Focus

1. A policy update races an in-flight login: each operation sees exactly one snapshot, including nested server API calls (Task 1).
2. Disabling enrollment with an existing TOTP account must retain the second-factor challenge, including recovery and reauthentication (Tasks 1, 3).
3. Two remaining admins concurrently demote/ban/delete one another: only one capacity-reducing transaction commits; rejected deletion never starts erasure cleanup (Task 2).
4. A mail provider accepts a request but the connection fails: account creation is retained and delivery is unknown, never automatically repeated or reported delivered (Task 4).
5. A user/detail view changes while a mutation settles: errors and password fields stay with the execution owner; only originating query keys invalidate (Tasks 5, 6).

**Interfaces:**

- `AuthPolicySnapshot = Readonly<{activationVersion: 0|1; revision: string; emailVerificationRequired: boolean; sessionDurationHours: number; twoFaEnabled: boolean; passwordMinLength: number}>`; revision is a stable hash of the validated effective tuple, with no secret input.
- `loadAuthPolicy(database?: AuthDatabase): Promise<AuthPolicySnapshot>` reads singleton `auth_policy_state` (`id=1`, `activation_version=1`, complete four-setting JSON snapshot, revision, activated_by/at). Absent activation returns version `0` and verification/enrollment `true`, lifetime `168`, minimum `8`, ignoring inert legacy drafts. Once activated, valid `AUTH_EMAIL_VERIFICATION` (`true|false|1|0`) overrides the activated DB snapshot, with declared ownership. Invalid active policy fails closed with `AUTH_POLICY_INVALID`; database failure is `AUTH_POLICY_UNAVAILABLE`, never interpreted as unactivated defaults.
- `applyAuthPolicy({settings:{emailVerificationRequired,sessionDurationHours,twoFaEnabled,passwordMinLength},expectedRevision,confirmed:true,idempotencyKey,actorId}): Promise<AuthPolicySnapshot>` requires a real full-admin session, validates all four effective values, locks the singleton and atomically writes settings, activation version `1`, revision and audit. GET `/api/admin/accounts/policy` returns `{active,pending,ownership}`; POST `/api/admin/accounts/policy/apply` is the only activation operation. Generic settings PATCH/import only stage validated pending auth drafts, even after activation; they never activate or replace the live tuple.
- `withAuthOperation<T>(run: (instance: PolicyAuth) => Promise<T>): Promise<T>` uses AsyncLocalStorage to pin policy and transaction context. `auth.handler` and **every** `auth.api` method delegate through this facade, preserving inferred overloads, `asResponse`, headers, and `$Infer` types. `PolicyAuth` is `ReturnType<typeof createPolicyAuth>`; no consumer receives an unguarded raw instance.

Cache only the latest immutable non-transactional factory result; in-flight calls retain their captured instance. Never cache an instance bound to a completed transaction.
