> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement S01–S08: effective updates, shared preparation, truthful batch outcomes, owned-service capabilities, safe core maintenance, and usable outage troubleshooting.

**Architecture:** The agent derives action decisions and owned-container inventory from trusted authority, then enforces those decisions again at execution. API jobs retain preparation/effect identities and project agent outcomes; the generated SDK drives Services controls. Preserve existing release replacement and configuration-generation workflows instead of adding a command endpoint.

**Tech Stack:** TypeScript, Fastify, Zod, PostgreSQL/Drizzle job records, Docker ops-agent, Commander CLI, React/MUI, generated SDK, Vitest.

**Spec:** `docs/superpowers/specs/2026-10-23-admin-instance-management-design.md` and binding `docs/superpowers/specs/2026-10-23-admin-control-protocols.md` (protocol sections cited below); master: `docs/superpowers/plans/2026-10-23-admin-instance-management.md`. ## Global Constraints

- All product work stays in this worktree; preserve unrelated work and existing public-provider behavior. One branch/PR; no merge or production deployment.
- Use Codex provider instances only for delegated work.
- Retain `IntegrationContext`, HTTP/upstream acquisition, attribution and source policy boundaries. Community integrations remain declarative; no uploaded code execution and no browser developer toolchain.
- Docker, registry credentials, privileged host files and host data writes remain behind typed ops-agent operations. No generic command, arbitrary path or raw environment-file editor is introduced.
- Core API routes use `registerCoreRoutes`, runtime admin guards beside auth declarations, strict schemas, audit events, explicit mutation identities and appropriate rate limits. Privacy roles retain their narrower authority.
- Contracts precede generated outputs. Serialize OpenAPI/SDK generation; never hand-edit generated files. Check actual response serialization.
- Preserve configuration writer ownership, revision CAS, admission fingerprints, durable operation identities, retained results, unknown outcomes and cancellation fences. No automatic mutation retries or unproven rollback/compensation.
- Use synthetic/public data in tests and UI verification. Never print secrets, place secrets in argv or logs, or copy private operator data into artifacts.
- Stream large transfers with bounded memory, disk budgets, timeouts, cancellation and cleanup. Opaque IDs cross trust boundaries; host paths do not.
- UI controls expose availability and reasons before submission. A successful admission means queued, not applied. Failed/partial/unknown work stays visible.
- Inspect the actual rendered desktop/mobile UI locally. Do not upload screenshots to the PR, as explicitly requested.
- Complete focused checks, full local verification, relevant disposable database and runtime checks, independent review, production builds and PR CI. Report any unavailable environment gate distinctly; do not replace runtime evidence with mocked assertions.

## Review Focus

1. A deselected container absent from the new Compose file must still be stoppable/readable only by verified ownership; forged labels or changed container identity must fail (Task 1).
2. A new generation or release pin between preparation and recreation must prevent stale application, including repeated job recovery (Task 2).
3. Failure after one completed service, fail-fast, or cancellation must preserve completed/failed/skipped identities without a success event (Task 3).
4. Replacing the API or edge while the browser disconnects must retain an externally observable result; the executing agent must never terminate itself (Task 4).
5. An agent outage, including the first server render, must show unknown state and leave full-admin troubleshooting navigation reachable (Tasks 5–6).

## Cross-plan interfaces

- `ServiceAction = "start" | "stop" | "restart" | "update" | "build" | "logs" | "pull" | "apply"`; `ServiceActionDecision = { available: boolean; execution: "direct" | "workflow" | "host"; reason: "disabled" | "not_owned" | "not_running" | "control_plane" | "host_only" | "unavailable" | "not_buildable" | null; workflow: "core-restart" | "system-update" | "coordinator-apply" | "coordinator-update" | null }`. A denied decision has a non-null reason; a direct available decision has null reason/workflow. An available workflow decision has null reason and a non-null workflow; `execution: "host"` is unavailable with `reason: "host_only"`. API/edge Restart selects `core-restart`; available application Update selects `system-update` only when existing checked-release eligibility permits it. Protected dependency lifecycle stays host-only. Never advertise a workflow solely because its route exists.
- New typed `services.inspect` is API-role synchronous, 15 seconds, maximum 256 services: `{ services: Array<{ serviceId: string; state: existingStackState; actions: Record<ServiceAction, ServiceActionDecision> }> }`. It returns only trusted registered services; acquisition failure throws. API adds `"unknown"` to its service status enum and returns `acquisition: { state: "available" | "unavailable"; reason: "ops_unavailable" | null }` plus `summary.unknown`.
- Move/re-export `HardlinkApplySummary` from `apps/api/src/services/admin-ops.ts` to controller-owned `packages/core/src/ops/service-results.ts` so the CLI and API import the same portable type; API preserves its current re-export for callers.
- `prepareServiceGeneration(ctx: JobContext, scope: string, options: { coordinatorMode: CoordinatorMode }): Promise<ServicePreparationResult>` uses the exact strict candidate and publication/follow-up split in protocol§5–6. Portable `CoordinatorMode = "ensure-running" | "require-running"`; `ServicePreparationResult = { revisionId: string; hardlinks: HardlinkApplySummary; coordinatorMode: CoordinatorMode }`. Start/Update selects ensure-running;09.6 Compose Render selects require-running. Mode, original revisions, sealed candidate identity and both preparation child identities are retained under `servicePreparation[scope]` before effects. Replays observe those identities; they never reconstruct a candidate or silently overwrite newer configuration.
- Export `prepareProspectiveConfiguration({actorId,expectedCurrentRevisionId,overlay,operationKey,signal?}): Promise<ValidatedConfigurationCandidate>`, `persistAndApplyProspectiveConfiguration(candidate,{coordinatorMode,signal?}): Promise<ProspectiveConfigurationReceipt>` and `withAdministrativeConfigurationWriter` exactly as protocol§5. All callers enter the API global writer before sorted integration locks; host effects then follow target→nonblocking transit→host writer→release store. Reentrancy requires the same branded live connection/context, never a boolean. Candidate payload, sealed bytes and source fingerprint are server-private; no later snapshot collector may replace them.
- Extend `service.start`, `service.recreate`, `service.recreateIsolated`, and `service.update` with `expectedConfigurationRevisionId: string` (the `cfg1_` schema). Every API-role call, including preparation's data-manager Start, supplies it; omission is a schema error, not a bypass. Agent checks it under shared target-lease and configuration writer ownership before effect. `service.update` returns `{ changed: true, revisionId: string }`, the resulting generation rather than its input condition; the API checkpoints this before any subsequent target. Only Update advances this condition; Start/recreate checks the exact prepared revision and never creates a fresh generation implicitly.
- M01 presets resolve to explicit canonical `serviceIds` at admission and store both `presetIds?: string[]` and expanded IDs in the job. Plan 09 owns the finite preset enum and resolver; agents never interpret a preset as shell text or silently broaden it on resume.
- M02 update uses `noDeps?: boolean` (default false); M03 build uses `motisImport?: boolean` (default false, meaningful only for `motis`); M04 pull is a distinct `action: "pull"`, never update with a suppressed recreate. Public log controls use `lines: number` (1–1000, default 200), `follow: boolean` (default true), `maxDurationSeconds: number` (1–900, default 900); only the agent adapter maps `lines` to ops `tail`, also bounded at 1000. Plan 09 owns public option exposure; reliability code preserves these exact fields in fingerprints, checkpoints and fixed argv.
