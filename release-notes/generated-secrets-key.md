## What changes

Secret settings saved in the admin panel (the SMTP password, the EmailLabs and
Lettermint credentials and the MapTiler key) are stored encrypted in their own
table instead of in clear among the system settings. The admin panel still
shows them only as configured and lets an administrator replace or clear them;
environment variables such as `SMTP_PASS` still take precedence.

The key that encrypts everything the API stores secret in the database (these
settings, the credential vault, personal timeline credentials and assisted
privacy-request locators) is now generated by `pnpm openmapx compose render`.
The render creates `infra/docker/secrets/secrets-key` once, as 32 random bytes
in 43 base64url characters, never replaces it, and mounts it only into the
`api` service, which reads it through `OPENMAPX_SECRETS_KEY_FILE`.
`OPENMAPX_SECRETS_KEY` is no longer read from `infra/docker/.env`, and the
former 64-character hex format is not accepted anywhere. Development without a
render may set `OPENMAPX_SECRETS_KEY` to a value in the new format; the API
refuses it beside a key file. A missing or wrong key now fails with a message
that says so.

## Who is affected

Every deployment and development setup that set `OPENMAPX_SECRETS_KEY`. No
released installation exists.

## Required action

Remove `OPENMAPX_SECRETS_KEY` from `infra/docker/.env` and run
`pnpm openmapx compose render` before starting the API; while the variable is
set beside the generated key file, the API uses neither and refuses to store or
read secrets. Secrets encrypted with
an old hex key cannot be decrypted and must be entered again. For a host-run
development API, set `OPENMAPX_SECRETS_KEY_FILE=../../infra/docker/secrets/secrets-key`
in `apps/api/.env` instead of a hex key.

Copy `infra/docker/secrets/secrets-key` alongside every off-host database
backup, as with `erasure-journal-key`, and put it back before the API starts
against a restored database. Without the same key a restored database's
secrets cannot be read.
